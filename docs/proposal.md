# Thesis Proposal

> Кваліфікаційний проєкт бакалавра
> Спеціальність F2 — Інженерія програмного забезпечення

---

## 1. Робоча назва проєкту

**UA:** Хмароорієнтована сервісно-орієнтована платформа автоматизованого планування подорожей та управління бронюваннями на основі методів комбінаторної оптимізації

**EN:** Cloud-Native Service-Oriented Platform for Automated Travel Itinerary Planning and Booking Management Based on Combinatorial Optimization Methods

---

## 2. Актуальність та проблематика

Наявні цифрові сервіси планування подорожей поділяються на два класи, кожен із яких має структурні обмеження.

**Клас 1 — генеративні асистенти на основі великих мовних моделей.** Такі системи коректно інтерпретують природномовний запит користувача, проте не гарантують фізичної реалізовності згенерованого плану: маршрут не верифікується на відповідність реальному часу переміщення між точками, годинам роботи закладів і бюджетним обмеженням як системі взаємопов'язаних умов. Результатом є правдоподібний, але нереалізовний артефакт.

**Клас 2 — транзакційні платформи бронювання.** Такі системи ефективно вирішують задачу пошуку й резервування окремої одиниці розміщення, проте не формують цілісного маршруту та не координують бронювання різнотипних закладів у межах однієї поїздки.

**Інженерна проблематика.** Побудова реалізовного маршруту є задачею маршрутизації з часовими вікнами (Vehicle Routing Problem with Time Windows), що належить до класу NP-важких. Формування розкладу бронювань персоналу закладу є задачею розподілу ресурсів з обмеженнями того ж класу складності. Обидві задачі характеризуються часом розв'язання, який неприпустимо утримувати в межах синхронного HTTP-запиту, що зумовлює необхідність асинхронної архітектури з чергами завдань, механізмами відмовостійкості та контуром спостережуваності за станом обчислювальних задач.

## 3. Сформована ідея продукту

**Тип системи за архітектурою:** хмароорієнтована сервісно-орієнтована веб-платформа з асинхронною подієво-керованою взаємодією компонентів, побудована за принципами Clean Architecture з ізоляцією доменного ядра оптимізації від інфраструктурних адаптерів.

**Декомпозиція на сервіси:**

| Сервіс | Відповідальність | Технологічне ядро |
|---|---|---|
| `api-gateway` | Автентифікація, авторизація (RBAC), маршрутизація запитів, rate limiting | Django REST Framework |
| `optimization-service` | Розв'язання задач комбінаторної оптимізації (VRPTW, розподіл ресурсів) | FastAPI + Google OR-Tools (CP-SAT) |
| `ai-orchestrator` | Інтерпретація природномовного запиту, формування множини кандидатів, генерація векторних представлень | Python, Gemini API |
| `notification-worker` | Асинхронна доставка сповіщень про зміну статусу бронювань | Celery worker |

Взаємодія між `api-gateway` та `optimization-service` реалізується асинхронно через брокер повідомлень із патерном «завдання — статус — результат», що забезпечує незалежне масштабування обчислювального компонента та стійкість системи до пікових навантажень.

**Ключове архітектурне рішення:** єдина математична модель комбінаторної оптимізації (CP-SAT) застосовується до двох структурно споріднених задач різних предметних областей — побудови маршруту подорожі та формування розкладу бронювань персоналу. Доменне ядро солвера ізольоване від конкретної предметної області через абстракцію моделі обмежень, що забезпечує повторне використання компонента без дублювання логіки.

## 4. Детальний опис функціоналу (Core Features)

**F1. Асинхронна генерація оптимізованого маршруту подорожі.**
Користувач формує запит у природномовній формі або через структуровану форму. `ai-orchestrator` інтерпретує намір, формує множину кандидатів місць із збагаченням геоданими. `optimization-service` розв'язує задачу VRPTW з урахуванням обмежень: години роботи закладів, реальний час переміщення між точками, бюджетний ліміт, максимальна тривалість активності за добу. Завдання виконується асинхронно з відстеженням статусу через polling або server-sent events.

**F2. Оптимізований розподіл ресурсів при бронюванні послуг.**
Запит гостя на бронювання послуги обробляється тим самим обчислювальним ядром із іншою конфігурацією обмежень: графік роботи персоналу, місткість ресурсу, тривалість обслуговування, вже підтверджені бронювання. Система призначає конкретного виконавця й часовий слот, мінімізуючи час очікування клієнта.

**F3. Мультитенантна реєстрація різнотипних закладів та подій.**
Узагальнена модель `Venue` з типізацією (готель, заклад харчування, торговельний заклад, музей) дозволяє реєструвати заклади без дублювання структур даних. Бронювальні ресурси (`Facility`) та персонал (`Staff`) підключаються опційно залежно від типу закладу. Окрема модель `Event` обслуговує сутності з обмеженим часовим вікном існування (фестивалі, виставки).

**F4. Рольова модель контролю доступу (RBAC) з ізоляцією даних орендарів.**
Три ролі з розмежованими правами: `traveler`, `business_admin`, `staff`. Реалізується ізоляція даних між орендарями — власник закладу отримує доступ виключно до сутностей власного закладу; порушення межі орендаря блокується на рівні шару доступу до даних, а не лише інтерфейсу.

**F5. Персоналізовані рекомендації на основі векторної схожості.**
Профіль користувача, подорож і заклад представляються у вигляді векторних вкладень (embeddings), що зберігаються в PostgreSQL із розширенням `pgvector`. Підбір релевантних закладів виконується через обчислення косинусної схожості з індексацією HNSW для забезпечення прийнятного часу відгуку при зростанні обсягу даних.

**F6. Механізм верифікованих відгуків із перевіркою права на публікацію.**
Публікація відгуку про заклад або подію дозволяється виключно за наявності підтвердженого факту завершеного досвіду: завершеного бронювання, завершеної подорожі з відповідним місцем у маршруті або зафіксованого відвідування події. Перевірка виконується на серверному шарі як інваріант доменної моделі.

**F7. Контур спостережуваності обчислювальних задач (Observability).**
Система збирає метрики виконання задач оптимізації: час розв'язання, кількість оброблених обмежень, частка задач без допустимого розв'язку, глибина черги завдань. Метрики експортуються у форматі Prometheus та візуалізуються на інженерних дашбордах Grafana. Наскрізне трасування запитів між сервісами реалізується засобами OpenTelemetry.

## 5. Попередній інструментарій та технологічний стек

### Мови програмування
- Python (backend-сервіси, обчислювальне ядро)
- TypeScript / JavaScript (клієнтський застосунок)
- SQL (аналітичні запити, міграції схеми)

### Архітектурні патерни
- Clean Architecture — ізоляція доменного ядра оптимізації від інфраструктурних адаптерів
- Service-Oriented Architecture — декомпозиція на автономні сервіси з чіткими контрактами
- Asynchronous Task Queue — обробка тривалих обчислювальних задач поза межами HTTP-циклу
- Repository Pattern — абстрагування шару доступу до даних
- Multi-Tenancy (shared database, isolated rows) — ізоляція даних орендарів
- Circuit Breaker — захист від каскадних відмов при недоступності зовнішніх API

### Фреймворки та бібліотеки
- Django, Django REST Framework — API-шлюз, автентифікація, доменна логіка
- FastAPI — сервіс оптимізації
- Google OR-Tools (CP-SAT solver) — розв'язання задач комбінаторної оптимізації
- Celery — асинхронне виконання завдань
- React (Vite) — клієнтський застосунок
- Pydantic — валідація контрактів між сервісами

### Бази даних та сховища
- PostgreSQL — основне реляційне сховище
- pgvector (розширення PostgreSQL) — зберігання та пошук векторних вкладень
- Redis — брокер повідомлень, кеш, сховище результатів завдань

### Зовнішні інтеграції
- Google Gemini API — інтерпретація природномовних запитів, генерація векторних вкладень
- Mapbox API — геокодування, розрахунок матриці відстаней, картографічна візуалізація
- Google Places API — збагачення даних про заклади

### DevOps та інженерія якості
- Docker, Docker Compose — контейнеризація та локальна оркестрація середовища
- GitHub Actions — конвеєр безперервної інтеграції (CI)
- pytest, coverage.py — автоматизоване тестування, вимірювання покриття
- Ruff, mypy — статичний аналіз коду та перевірка типів
- Trivy — сканування образів контейнерів на відомі вразливості
- Prometheus, Grafana — збір та візуалізація метрик
- OpenTelemetry — наскрізне розподілене трасування
- Alembic / Django Migrations — версіонування схеми бази даних

### Документування
- Documentation as Code — документація зберігається у Git поруч із вихідним кодом
- OpenAPI (drf-spectacular) — автоматична генерація специфікації API
- Architecture Decision Records (ADR) — фіксація архітектурних рішень
- C4 Model — візуалізація архітектури на рівнях Context, Container, Component

## 6. Очікувані результати

1. Працездатна платформа з рольовим розмежуванням доступу та ізоляцією даних орендарів.
2. Обчислювальне ядро оптимізації, застосоване до двох структурно споріднених задач різних предметних областей.
3. Асинхронний контур обробки завдань із відстеженням статусу та обробкою відмов.
4. Автоматизований конвеєр CI зі статичним аналізом, тестуванням і скануванням вразливостей.
5. Контур спостережуваності з інженерними дашбордами метрик обчислювальних задач.
6. Комплект технічної документації: ADR, C4-діаграми, специфікація OpenAPI.
7. Пояснювальна записка з формалізацією математичної моделі та результатами навантажувального тестування.
