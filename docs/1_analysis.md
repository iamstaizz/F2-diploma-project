# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ТЕХНІЧНЕ ЗАВДАННЯ

## 1.2 Аналіз існуючих аналогів

Для визначення архітектурних вимог до системи Roame проаналізовано три програмні продукти, що вирішують суміжні задачі планування подорожей та бронювання: Wanderlog, Booking.com і Tripadvisor. Аналіз виконано з позиції інженерної системи: розглянуто архітектурний патерн, протоколи обміну даними, стек даних та відомі архітектурні обмеження (Technical Bottlenecks). Оцінку інтерфейсу користувача та комерційних характеристик не проводилося.

### 1.2.1 Wanderlog

**Архітектурний патерн.** Система реалізована як гібридна сервіс-орієнтована архітектура (SOA) з монолітним ядром, у якому зосереджено бізнес-логіку планування. Для підтримки спільного редагування маршрутів у реальному часі застосовано подієво-кероване (Event-Driven) опрацювання на рівні сесій. Масштабованість обмежена необхідністю утримання довготривалих stateful-з'єднань для колаборативних сесій.

**Протоколи передачі даних.** Взаємодія клієнта із сервером здійснюється через REST API для транзакційних операцій (CRUD) та WebSockets (або Server-Sent Events) для двосторонньої синхронізації стану редагування маршруту.

**Базовий стек даних.** Основним сховищем є реляційна СУБД PostgreSQL, доповнена NoSQL-рішеннями для обробки колаборативних даних. Кешування та керування сесіями забезпечує Redis. Консистентність даних у реальному часі досягається механізмами Operational Transformation (OT) або Conflict-free Replicated Data Type (CRDT).

**Технічні обмеження (Technical Bottlenecks).** Необхідність утримання відкритих WebSocket-з'єднань для кожного активного користувача зумовлює високе споживання оперативної пам'яті (RAM) на стороні серверної частини. Складні геопросторові запити супроводжуються зростанням Latency, оскільки визначення релевантності локацій виконується на основі класичних індексів без застосування векторного пошуку.

### 1.2.2 Booking.com

**Архітектурний патерн.** Система побудована як високонавантажена розподілена мікросервісна архітектура. Історично вона еволюціонувала від монолітної реалізації на Perl до значної кількості ізольованих мікросервісів. Масштабування виконується горизонтально, що супроводжується суттєвими накладними витратами на інфраструктурну оркестрацію (Kubernetes) та Service Mesh.

**Протоколи передачі даних.** Зовнішня маршрутизація та інтеграція з партнерами здійснюються через HTTP/REST та GraphQL. Міжсервісна взаємодія оптимізована за допомогою gRPC (Protobuf для бінарної серіалізації) та асинхронних черг повідомлень (Kafka, RabbitMQ) для публікації подій бронювання.

**Базовий стек даних.** Для транзакційних даних використовуються шардовані та репліковані кластери MySQL/PostgreSQL, для інтенсивного запису (логування, події) — Cassandra. Для пошукових індексів застосовується модель Eventual Consistency, тоді як ядро бронювання вимагає ACID-транзакцій із використанням двофазних комітів (2PC) або патерну Saga.

**Технічні обмеження (Technical Bottlenecks).** Під час пікових навантажень (Flash sales) виникає ризик Race conditions, що може призводити до перевищення кількості доступних бронювань (overbooking). Причиною є компроміс за CAP-теоремою на користь Availability відносно Consistency на окремих вузлах. Додатковими обмеженнями є складність розподіленого трейсингу та висока вартість підтримки інфраструктури консистентності даних між великою кількістю баз даних.

### 1.2.3 Tripadvisor

**Архітектурний патерн.** Система має розподілену архітектуру з акцентом на інтенсивне читання (Read-Heavy). Патерн CQRS (Command Query Responsibility Segregation) застосовується для розділення потоків запису відгуків та читання (агрегація рейтингів, пошук).

**Протоколи передачі даних.** Для агрегації даних з доменних сервісів (авіаквитки, готелі, ресторани) в єдиний граф використовується GraphQL Federation. Застарілі (legacy) модулі взаємодіють через REST API.

**Базовий стек даних.** Джерелом істини є PostgreSQL. Для повнотекстового пошуку та гео-запитів застосовуються кластери Elasticsearch, для офлайн-аналітики — Hadoop/Spark (MapReduce). Кешування реалізовано через Memcached та Redis.

**Технічні обмеження (Technical Bottlenecks).** Складність інвалідації кешу (Cache Invalidation) зумовлює появу Stale Data, коли користувачам відображаються неактуальні ціни або статуси. Відсутність нативної підтримки векторного пошуку (Embeddings) у базовій архітектурі обмежує систему інвертованими індексами (BM25), що знижує семантичну точність обробки складних природномовних запитів щодо планування подорожей.
